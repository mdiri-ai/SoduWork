# SoduWork 企业能力包编写指南（schemaVersion 1）

**简体中文** · [English](plugin-authoring.en.md) · [文档导航](README.zh-CN.md)

应用作者可从“应用 → 添加 → 开发应用”使用内置开发技能，它继承插件开发助手的基础规范，并提供独立窗口、公共 H5 SDK、页面与对话/刷新联动及验证流程。应用草稿根级使用 `template: "app"`，声明真实 HTTP(S) 的 `ui.contributions` / `workspace.navigation` 页面，`source.openMode` 为 `workspace`；本地 HTML 资源不会由安装器自动启动。未声明窗口大小时默认 1280×800，仍可最大化/全屏。安装、版本和 `.soduwork-plugin` 导出继续使用本指南的同一链路；“安装并打开”进入应用独立窗口。详见[应用开发技能](../skills/app-developer/SKILL.md)。

> 这份文档面向插件作者。SoduWork 插件是可安装、可授权、可发布的企业能力包，可以包含
> Instructions、Skill、MCP、工具、权限声明与可选工作流。可运行样例见 `hub-backend/plugins/*.json`。

插件不等于工作流：单步方法、知识型 Skill、系统连接器可以直接从对话或任务调用；只有需要
多 Agent 协作、人工门禁、质量检查、发布或断点恢复时，才声明工作流。运行时会把直接任务调用
编译成内部执行计划，但目录和详情不会把它伪装成业务工作流。

## 先理解三个对象

| 对象 | 回答的问题 | 可变性 |
|---|---|---|
| `PluginVersion` | 包含哪些能力、开放哪些入口、可选流程如何执行 | 不可变；内容变化必须升 SemVer |
| `PluginBinding` | 在这个组织/项目里如何连接 MCP、密钥、Agent、模型和 Runner | 可配置；升级版本前做兼容性分析 |
| `WorkflowRun` | 这一次任务跑到哪里、实际谁执行、留下什么证据 | 持久化；失败可从准确断点恢复 |

因此不要把公司地址、某台机器、个人模型或密钥写死进插件。插件定义可移植的方法；
绑定把方法落到企业环境；运行锁定版本、路由、上下文和证据。

生命周期：

```text
客户端插件工坊或源码仓库编写
  → 本地打包
  → 导入前静态预检
  → 隔离区
  → 管理员能力审查
  → 绑定组织或项目
  → 真实环境模拟
  → 任务启动
  → 逐节点执行、验收、恢复和沉淀
```

### 两种作者入口

- 普通员工在客户端“插件 → 制作个人插件”编写方法，也可以打开内置“插件开发助手”，让 SoduWork
  通过对话生成 `soduwork-plugin-draft.json`，再导入并安装到本机。制作、预检、安装、启停和删除都在
  客户端完成，默认仅自己可见，不需要管理员，不会自动上传。
- 专业作者在客户端插件工坊或受版本控制的源码仓库中维护插件，也可导入 SoduWork/Codex/Claude 插件包。
  复杂 DAG 应在代码中维护并接受代码评审，避免在线画布产生无法审查的隐式配置。

> 管理端不是插件编辑器。它只提供起步包下载与候选包导入，并负责静态预检、隔离、评测、审批、
> 发布、绑定、回滚和审计。管理员看到的安装参数与节点协议都是不可变版本的只读合同。

个人插件确认适用后，作者可以主动“上传到企业”，选择全公司或指定成员。Hub 会重新预检并生成
不可变候选版本，先进入隔离区；管理员审查、发布后，目标成员能在企业目录发现。员工按需安装到
个人对话工具箱，管理员则把不可变版本绑定给任务或自动化。
上传不会改变或删除本机版本，也不会把个人插件数据静默同步到企业。
首次从某台客户端上架时，客户端会用系统安全存储中的 Ed25519 私钥签署不可变包，并把公钥候选
随提交送入隔离区。Hub 会先验证候选公钥确实能验过当前包，但不会因此自动信任。插件管理员须在
版本审查中核对 Key ID 与 SHA-256 指纹并显式登记；登记后 Hub 再读取原包验签。登记发布者也不
等于发布插件，版本仍要经过能力审查、评测和明确启用。

“我的申请”在提交新版本后仍保留每个已提交版本及其审核历史。每条记录打开对应的确切版本，可查看此前的审核决定和反馈。已上架插件下架时，应用内通知会发给发布者和仍安装该插件的账号；撤销某个版本时，通知发给其发布者和安装该版本的账号。通知与状态变更一同保存，离线后重新连接仍可查看；重复提交未改变状态的操作不会重复通知。插件通知遵循接收人的账号和公司范围。

## 个人插件与企业发布边界

```text
客户端对话/表单创建
  → 本机静态预检
  → 私有安装和试用
  → 作者主动上传（可选）
  → 企业隔离区
  → 管理员审查与发布
  → 全公司或指定成员发现并按需安装
  → 管理员绑定项目/组织后供任务与自动化使用
```

- 个人插件保存在当前客户端的数据目录，身份为 `local:<uuid>`，离线也能列出和使用。
- 同一个 SemVer 内容不可变；内容变化必须提升版本号，避免历史会话和任务发生漂移。
- 插件定义不接收密码、Token、私钥或 API Key。企业凭据只通过绑定的 Secret Reference 使用。
- “插件开发助手”本身也是内置个人插件，只负责把工作方法整理成安全草稿，不绕过预检和上架审查。
- 企业版本的可见范围固化在版本上。指定成员只能选择同组织的有效账号，目录和运行时都会再次校验。
- 删除或停用本机版本不影响已经发布的企业版本；企业发布也不会覆盖个人草稿。
- 企业发布与受众决定“谁能发现”；个人安装决定“谁把它加入普通对话工具箱”。
- 安装态跟随企业账号跨客户端同步，并固定员工已接受的不可变版本；企业切换版本后必须明确确认升级。
- 任务和自动化始终由企业绑定治理，不受员工个人安装、停用或升级选择影响。
## 包格式与不可变版本

`.soduwork-plugin` 是 zip（不超过 10 MB、300 个文件），根目录必须有 `plugin.json`。
也可以把 `workflow` 拆到同目录的 `workflow.json`。

```json
{
  "schemaVersion": 1,
  "key": "weekly-brief",
  "version": "1.0.0",
  "name": "团队周报整理",
  "description": "把本周任务、成果和风险整理成可提交的周报",
  "author": "你的团队",
  "instructions": "读取本周工作事实，按成果、风险、下周计划生成清晰周报；不得虚构。",
  "entrypoints": {
    "conversation": true,
    "task": true,
    "automation": false
  },
  "inputs": [
    {
      "key": "goal",
      "type": "textarea",
      "label": "业务目标",
      "description": "目标、完成标准与边界",
      "placeholder": "说明要解决的问题和验收标准",
      "required": true
    }
  ],
  "capabilities": {
    "skills": [],
    "mcpServers": [],
    "secrets": [],
    "runtime": [],
    "network": false
  }
}
```

- `key` 只允许小写字母、数字和短横线，是插件的稳定身份。
- 平台内置身份显示为 `soduwork/<key>`；企业身份显示为 `org:<org-id>/<key>`。显示名称可以优化，稳定身份不可漂移。
- 同一平台或同一企业内不允许重名 key；不同企业可以安全使用相同 key，数据库会在并发导入时强制去重。
- `version` 必须是 SemVer。同一版本内容不同会被拒绝，不会静默覆盖。
- `entrypoints` 声明允许从对话、任务或自动化调用；直接能力包可以完全不写 `workflow`。
- 没有工作流时，至少提供 `instructions`、Skill 或 MCP，让平台知道如何可靠使用这项能力。
- 压缩时间、顺序和压缩算法不会改变包身份；平台按文件名与内容生成规范 SHA-256。
- 导入不等于信任，更不等于执行。导入阶段不会运行脚本或连接网络。

### 应用窗口基础信息 `appWindow`（可选）

应用没有声明窗口尺寸时，默认以 **1280×800 逻辑像素**在主窗口所在屏幕居中打开；较小屏幕自动适配，避开任务栏。一般应用无需填写，用户不必到应用设置或配置中心调整。

只有需要特殊默认尺寸时，在 `soduwork-plugin-draft.json` 或包内 `plugin.json` 的基础信息层添加 `appWindow`，与 `name`、`version` 同级：

```json
{
  "name": "示例云端资料库",
  "version": "1.0.0",
  "appWindow": {
    "width": 1280,
    "height": 800,
    "minWidth": 480,
    "minHeight": 360,
    "maxWidth": 2680,
    "maxHeight": 17800,
    "rules": [
      { "maxScreenWidth": 1366, "width": "100vw", "height": "100vh" }
    ]
  }
}
```

以上是基础信息片段，其余必填字段仍按完整插件格式提供。数字默认 px，支持 px/vw/vh；100vw×100vh 表示目标显示器的可用逻辑区域。`maxWidth/maxHeight` 只限制默认打开尺寸，仍允许手动最大化或全屏；`minWidth/minHeight` 用于普通缩放，小屏幕会适当降低。`rules` 最多 12 条，按屏幕可用逻辑宽度从上到下采用第一条匹配规则，闭区间 `minScreenWidth/maxScreenWidth` 可分别留空，规则未填写的宽高沿用默认值。

此配置随不可变版本和安装包传播，编辑旧插件会保留；修改应升 SemVer。已打开的应用保留页面和侧栏，关闭后重新打开才应用新版尺寸。

### 流程身份 `process`（可选）

企业级研发流程要在所有选择入口（建任务、转发、对话 `/`、插件中心）亮明身份，
并写清最终交付到哪个环境——选流程的人不该等跑起来才知道这条流程会动什么：

```json
"process": {
  "enterprise": true,
  "label": "企业研发流程",
  "route": "AI 修改 → Gerrit 评审 → 合并 → 公司 CICD 发布",
  "environments": [
    {"label": "QA 环境（示例）", "scope": "company"}
  ]
}
```

- `enterprise` 为真时客户端与管理端都会打出徽标；`label` 默认「企业流程」。
- `route` 是一句话的流程路线（≤200 字），`environments` 最多 8 项，
  `scope` 只接受 `company` / `department` / `project`。
- 老版本没有声明时，平台按工作流形状推断：含 `merge`、`deploy`、`deploy_chain`
  节点即视为企业流程（不用重新导入也能带上标识）。

## 能力组件、依赖与权限摘要

平台会从不可变包自动生成一份可审查报告，不要求作者再维护一份容易漂移的副本：

- **组件清单**：工作说明、Skill、MCP 连接、可选工作流，以及暂不支持的第三方组件。
- **依赖清单**：外部 Skill、MCP、逻辑密钥和环境；只保存名称或引用，不保存密钥值。
- **权限摘要**：网络、受控脚本、逻辑密钥和兼容性阻断，并给出低、中、高风险说明。
- **调用入口**：对话、任务、自动化。关闭已有入口属于破坏性升级，新开放入口必须重新审查。

组件清单描述“包里有什么”，权限摘要描述“运行时会获得什么”，绑定描述“在这家公司具体接到哪里”。
三者不能混成一张配置表，也不能因为绑定完成就扩大插件清单声明的能力上限。

## 可选工作流：节点 DAG

只有复杂、可恢复、需要明确交接或门禁的工作才添加 `workflow.nodes`。

节点形状：

```json
{
  "key": "implement",
  "type": "ai",
  "name": "实现与自测",
  "dependsOn": ["understand"],
  "inputs": [],
  "outputs": [],
  "capabilities": {},
  "config": { "timeoutSeconds": 3600 },
  "retry": { "maxAttempts": 2 }
}
```

DAG 只用 `dependsOn` 表达，必须无环，节点数 1～100。
返工使用失败策略和重试，不用回边。每个节点最多重试 5 次。
`ai` / `ai_review` 可在 `config.timeoutSeconds` 声明 60～86400 秒的运行上限；
到时仍未完成会停止当前执行、保存超时与停止结果，并按本节点重试策略处理。

### 支持的节点类型

| type | 执行位置 | 用途 |
|---|---|---|
| `ai` | Runner 上的 Agent CLI | 分析、开发、写材料、使用 Skill/MCP |
| `ai_review` | 独立 Runner/Agent 路由 | AI 审查，不能由自己的结果自我授权 |
| `spec` | 人 | 需求基线确认 |
| `human_review` | 人 | 业务审阅或验收 |
| `approval` | 人 | 高风险授权 |
| `quality` | Runner 干净工作区 | 构建、测试、质量门禁 |
| `script` | Runner 干净工作区 | 受控命令执行与留证 |
| `tool` | Hub 受信工具注册表 | `http_check`、`notify` 等 |
| `merge` | Hub/Runner | 已满足策略后的自动合并 |
| `deploy` | Runner | 发布到绑定配置的环境 |
| `deploy_chain` | Hub 编排 | 按企业环境链发布、检查、验收、回滚 |
| `validate` | Hub | 声明式制品规则校验 |
| `condition` | Hub | 按运行输入分流 |
| `publish` | Hub | 结单和交付回执 |

## 任务工作流在普通会话中执行

普通插件对话与完整任务工作流共用同一套消息、工具、附件和成果组件，不再打开另一套任务聊天页。

- 对话中输入 `/创建任务`：确认任务草稿后，把任务与当前会话关联；正文、验收标准和附件作为任务轮次发送。
- 从待办或 AI 工作台“查看对话”：打开任务已经关联的原会话，不创建替代会话，也不因查看而启动执行。
- 手动添加任务与派活到会话共用队列；前一项完整执行结束后，后一项才发送，等待审批不算完成。
- 多 Agent 工作流由节点路由选择 Agent；不要让用户再选一个 Agent 来覆盖所有节点。
- 工作流每个 AI 节点的说明、工具运行和输出实时回到原消息流，不仅在结束后给一张详情结果。
- 人工确认在对话内完成；未批准、撤销或缺少有效决定时，后续节点不得执行。独立门禁菜单不是运行依赖。
- 公司/上级组织发布并绑定的通用插件可由下属部门按授权使用；项目限制、指定受众和不同公司之间的隔离仍然有效。

`/插件名` 的普通对话试用不等于启动工作流。需要真实节点执行、审批和恢复时，应明确创建任务并选择该工作流；不能用一段 AI 文字假装已经审批或发布。

## 跨 Agent 上下文：显式交接，不拼接聊天记录

上游用 `outputs` 声明稳定产出，下游用 `inputs` 只引用直接上游已声明的产出：

```json
{
  "key": "understand",
  "type": "ai",
  "name": "理解与规划",
  "config": {
    "prompt": "形成计划并写入 deliverables/plan.md"
  },
  "outputs": [
    {
      "key": "plan",
      "kind": "file",
      "path": "deliverables/plan.md",
      "label": "执行计划",
      "required": true
    }
  ]
}
```

```json
{
  "key": "implement",
  "type": "ai",
  "name": "实现",
  "dependsOn": ["understand"],
  "inputs": [
    {
      "key": "plan",
      "fromNode": "understand",
      "outputKey": "plan",
      "label": "已确认计划",
      "required": true
    }
  ],
  "config": {
    "prompt": "依据上游计划实现并自测"
  },
  "outputs": [
    { "key": "change", "kind": "git", "label": "代码提交", "required": true }
  ]
}
```

支持的产出 `kind`：

- `file`：精确路径文件，平台校验文件名和可用性。
- `git`：工程提交；工程任务优先交 Git，不用压缩包替代。
- `evidence`：检查、截图或其他证据。
- `url`：可访问成果地址。
- `decision`：结构化结论文件，每个节点最多一项。

`decision` 的内容必须是 UTF-8 JSON，而非自然语言 Markdown。新插件建议使用 `.json` 后缀；
历史已发布版本即使声明 `.md`，仍保留原路径并按 `decision` 类型校验，不静默修改不可变版本。

```json
{
  "schemaVersion": 1,
  "outcome": "proceed",
  "reasonCode": "ready",
  "summary": "已经逐项核对原始材料与交付文件",
  "evidence": ["原始记录第2段对应纪要第3节"],
  "nextAction": ""
}
```

未达标或无法核对时必须返回 `outcome: "blocked"`、非 `ready` 的原因和具体 `nextAction`。
文件类 `ai_review` 必须声明必交 `decision`，平台按本次节点的证据校验；代码类审查仍需固定
Git 版本及 `code-review.json`，两者不会互相替代。两类 AI 复核都不能替代后续人工批准。

运行时 SoduWork 生成有边界的上下文快照，保存输入 key、来源节点、产出 key、校验和与是否截断。
不同 Agent 不共享隐式终端历史，也不会把整段旧会话无限塞给下一个模型。

## 每个节点使用不同 Agent 和模型

插件包可以提供默认 `agentKind`，但推荐把具体路由留给绑定：

1. 绑定设置整条流程的默认 Agent、模型、不可用时策略和 Runner 标签。
2. 对 `ai` / `ai_review` 节点单独覆盖 Agent、模型和 Runner 标签。
3. 真实启动前逐节点模拟，显示“期望路由 → 实际在线执行机”。
4. `strict` 要求严格使用指定底座；`best-effort` 可在不可用时选择合规替代。
5. 每次运行保存期望路由、实际 Agent、模型、主机和降级原因。

这样同一插件可在 A 公司用 Codex，在 B 公司用 Pi，在隔离网络里用 OpenCode，而不制造多个方法副本。

## 最小权限、Skill、MCP、网络和密钥

插件先声明能力上限，AI 节点再声明本关使用的最小子集：

```json
{
  "capabilities": {
    "skills": ["requirements-analysis", "office-docs"],
    "mcpServers": ["jira", "gitlab"],
    "secrets": ["JIRA_TOKEN"],
    "runtime": ["browser", "office"],
    "network": true
  },
  "workflow": {
    "nodes": [
      {
        "key": "analyse",
        "type": "ai",
        "config": { "prompt": "分析需求并形成基线" },
        "capabilities": {
          "skills": ["requirements-analysis"],
          "mcpServers": ["jira"],
          "secrets": ["JIRA_TOKEN"],
          "runtime": ["browser"],
          "network": true
        }
      }
    ]
  }
}
```

- 节点不能申请插件未声明的能力，导入时会直接拒绝。
- 没写节点 `capabilities` 的旧插件暂按插件级能力继承；新插件应始终显式写最小子集。
- Skill 只下发本关需要的项；MCP 先限制到本关需要的服务，再由企业绑定从真实工具目录
  逐项批准具体工具。未批准的工具不会出现在 `list` 中，直接调用也会被 Hub 与 Runner
  两侧拒绝；插件不能用底座自己的全局 MCP 配置绕过。
- 每轮对话使用短期签名票据携带不可篡改的调用预算；Hub 会限制总调用数、并发数和
  工具清单读取次数，并在连接连续失败时短暂熔断。
- 工作流下发给 Runner 的每个连接都携带统一的超时与返回大小预算；桥接层在任何 Agent
  底座之前执行，避免慢连接或超大结果拖垮会话。
- `runtime` 声明执行机事实：`files`、`terminal`、`repository`、`browser`、
  `office`、`computer`。它参与逐节点模拟和 Runner 选机，缺失时不会偷偷回落到
  不具备能力的 Hub 服务器。
- `network` 是可审查能力声明，并在底座支持时收紧工具策略；企业 Runner 仍可用网络策略做更强隔离。
- `secrets` 只写逻辑环境变量名。绑定页映射到同组织、已启用、已探活的 `runner-env`
  SecretReference。Hub 只传“目标变量名 → Runner 来源变量名”，密钥值不离开 Runner，
  只注入当前节点的子进程，不写入插件、绑定、运行证据或日志。

## 命令节点

`quality` 与 `script` 使用同一安全形状，argv 直接执行，不经过 shell：

```json
{
  "key": "build",
  "type": "quality",
  "name": "构建与测试",
  "dependsOn": ["implement"],
  "config": {
    "commands": [
      { "name": "安装依赖", "argv": ["js:install"], "timeoutSeconds": 600 },
      { "name": "构建", "argv": ["js:build"], "timeoutSeconds": 600 },
      { "name": "测试", "argv": ["js:test"], "timeoutSeconds": 900 }
    ]
  },
  "retry": { "maxAttempts": 2 }
}
```

`js:install`、`js:ci`、`js:build`、`js:test`、`js:type-check` 会按仓库当下的
packageManager 或 lockfile 选择真实命令。工作目录只能是仓库内相对路径。
质量节点默认检查跨包管理器锁文件、运行产物、异常大文件等变更卫生。

## 预检、模拟与信任

- **导入前预检**：包结构、版本、DAG、命令、输入输出引用、能力子集、敏感配置。
- **结果契约**：平台从每个节点声明的 `outputs` 形成版本级结果契约；每项都带来源节点、
  类型、路径和是否必交，运行时按同一契约验收。
- **发布评测**：清单可声明至多 20 个 `evaluations`。每项包含代表性
  `instruction`、无凭据 `inputs`、可判断的 `criteria` 和
  `expectedOutputs`；它们随不可变版本保存，变更时必须重新审查。
- **真实评测与发布门禁**：管理员为评测选择 Agent、模型、Runner 标签和密钥引用，
  平台在隔离工作目录执行并保存不可变用例快照、实际执行位置、产物大小与 SHA-256。
  结果契约满足后仍需人工给出通过结论；同一用例一旦重新运行，新运行会立即取代旧结论。
  声明了评测的版本必须全部通过才能启用；未声明评测只能由管理员明确确认风险后发布，
  员工目录会区分“已验证”和“已审查”。
  发布评测默认是零副作用执行，因此代表性用例应优先验收 `file`、`evidence` 或
  `decision`。如果把 `git` / `url` 声明为必交，但没有专用沙箱产生真实证据，
  门禁会阻断，绝不会把“未执行”当作“已通过”。
- **隔离导入**：创建不可变版本，但不执行、不信任、不绑定。
- **能力审查**：管理员查看 Skill、MCP、网络、密钥、脚本和适配器限制。
- **绑定模拟**：用真实项目检查仓库、环境、密钥引用、在线 Runner 和每个 AI 节点路由。
- **启动前快照**：运行锁定插件版本、绑定、节点配置和输入，后续升级不会让运行中流程漂移。

配置尚未就绪时可以先保存草稿，但模拟会列出 blocker。真正运行到缺配置的关卡会停止，
补好后从失败节点继续，不会无意义地重新做前面的 AI 工作。

## 版本升级规则

| 级别 | 典型变化 | 行为 |
|---|---|---|
| safe | 新增不破坏旧契约的节点 | 预检通过后可升级 |
| review | prompt/config、依赖、Skill/MCP/密钥/网络能力变化 | 重新审查并模拟 |
| breaking | 删除节点、改变节点类型、删除必需产出、改变输入引用、新增必填输入 | 必须查看影响并明确确认 |

旧运行始终引用旧快照；升级只影响明确切换到新版本的绑定。

## 失败分类与断点恢复

插件运行详情会把失败分为配置、授权、基础设施、契约、升级人工、质量和执行错误，
给出下一步动作。只有当前失败节点可以重试，旧失败尝试保留为证据但不会出现误导性按钮。

- 环境、仓库、密钥或权限错误：修配置后重试本关，不回卷开发。
- 产出契约或质量错误：按插件策略重做相应业务节点。
- AI 无法给出确定结论：进入人工处理，不重复消耗同一轮模型。
- AI 超过节点运行上限：尝试停止当前执行，按基础设施故障重试，并保留超时与停止证据。
- 每次重试创建新 attempt，旧日志、路由、上下文校验和和证据不覆盖。

## Codex 与 Claude 插件导入

SoduWork 能识别 `.codex-plugin/plugin.json` 与 `.claude-plugin/plugin.json`，转换成统一不可变
能力包模型。能映射的 Instructions、Skill、Agent 和真实工作流会进入能力报告；Hook、任意二进制或无法安全表达的
组件不会静默执行，而会显示为适配提醒或阻断项。导入成功不代表外部插件全部语义都已支持，
必须查看预检报告并模拟。


## 对话中通过 `/` 快速使用

员工在“新建”对话中输入 `/`，可以选择本机已启用的个人插件，也可以选择当前企业已发布、
本人可见、已绑定且已安装当前版本的企业插件。个人插件由客户端从本机不可变版本解析；企业插件
由 Hub 重新校验组织、受众、信任、绑定和个人安装。企业切换绑定版本后，目录只提示待升级，
不会静默替换员工已经接受的版本；确认升级后，新版本才能进入后续普通对话。选择结果按
**每一轮消息**固定为版本快照，排队、切换会话或后续升级都不会改变已经发送的这一轮。

- 快速使用只把插件的方法、质量标准和 AI 节点说明用于当前对话，不启动脚本、审批、合并或发布。
- 个人插件只用于当前客户端的对话试用，不冒充任务或自动化入口。需要多 Agent、节点级模型、证据
  关卡、重试和环境发布时，应先上传为企业候选版本，完成审查和绑定，再从任务运行完整工作流。
- 项目插件只在唯一适用项目或明确项目上下文中可用；多项目歧义会被阻止。
- 绑定配置、SecretReference、密钥值和包路径不会进入对话；历史仅展示名称、版本和作用域。
- 一轮最多选择 3 个插件，服务端会重新校验状态并记录审计，客户端选择不能绕过授权。

因此 `/插件` 是“立即采用企业工作方法”，任务插件是“受控执行完整企业流程”，两者共用
同一份已发布版本，但不会混淆执行事实。

## 自动化入口

插件清单中的 `entrypoints.automation` 表示该版本可以被员工的“自动化”计划调用。
计划只保存经过审批的不可变绑定 ID 和插件声明的普通输入；Secret 不进入计划，而是在
每个节点执行时从绑定的 SecretReference 最小化注入。

已升级客户端的本机普通自动化会创建普通会话，把整理好的任务内容、参数和已锁定插件快照
作为一轮消息发送，不额外创建业务任务。显式企业工作流绑定、远程派活与旧客户端仍沿用受控
任务执行合同；不要把这一兼容路径描述为所有自动化都必须先建任务。

完整工作流仍由同一套插件引擎执行，节点级 Agent/模型、类型化上下文、证据、人工确认、
重试和任务状态与手动启动保持一致。插件被停用、撤销授权、
缺少必填输入或运行条件未就绪时，计划会失败并留下可读原因，不会静默改成普通 Agent 执行。

## 发布前检查清单

- [ ] key 稳定，内容变化已升 SemVer。
- [ ] 每个 AI 节点有清晰 prompt、60～86400 秒运行上限和显式最小 capabilities。
- [ ] 跨 Agent 信息用 outputs/inputs 交接，没有靠“记住前面对话”。
- [ ] 工程成果声明为 git，文件成果写精确相对路径。
- [ ] AI 审查与实现节点分开；人工只保留业务验收或高风险授权。
- [ ] 环境、端口、机器、模型、账号和密钥没有写死。
- [ ] 质量命令使用 argv 数组，工作目录在仓库内。
- [ ] 导入前预检全绿，真实项目模拟无 blocker。
- [ ] 绑定升级影响已经检查。
- [ ] 至少做过一次成功、一次失败修复后续跑的端到端验证。

## 打包

### 本机草稿的随包资源

插件开发助手可以在当前会话工作目录生成模板、示例、脚本、素材、参考文件和页面文件，
与 `soduwork-plugin-draft.json` 同目录保存。草稿只声明相对路径，客户端从该会话登记的输出收集真实文件：

```json
{
  "resources": [
    { "path": "templates/report.md", "kind": "template" },
    { "path": "examples/input.json", "kind": "example" },
    { "path": "scripts/render.py", "kind": "script" }
  ]
}
```

- 最多 64 个文件，合计 8MB。允许目录为 `templates/`、`examples/`、`assets/`、
  `scripts/`、`references/`、`ui/`；拒绝越界路径、符号链接/联接点、密钥文件和明显凭据。
  凭据扫描不是完整安全审计；作者和企业审核仍须核对文件内容。
- 手动导入时，在客户端的系统文件选择器中选择 JSON 草稿，客户端以该文件所在目录为边界，
  收集草稿声明的相邻模板和示例。缺文件或路径越界会报错，不会静默省略资源。
  也可选择 ZIP / `.soduwork-plugin` 整包；导入文件上限为 24MB，资源内容仍受上面的 8MB 限制。
  新增文件选择接口需要客户端主进程重新启动后加载；旧进程期间仍可导入已内嵌资源的 JSON 或整包。
- 安装时把内容和 SHA-256 随版本保存。导出的可移植 JSON 包含 Base64 内容；跨设备导入
  不依赖作者的本地路径。同版本修改文件会被拒绝，需增加版本号。
- 本机对话启用插件时，在该会话工作目录的 `.soduwork/plugins/<key>/<资源摘要>/` 准备资源，
  将目录位置交给当前轮次。模板应复制后编辑；已经修改的缓存不会被静默覆盖。
- 上传生成的企业包在 `skills/<key>/` 下携带相同资源，包内清单验证路径、大小与摘要。
  回导能保留资源字节；这不表示所有外部插件语义或整个包逐字节往返不变。
- 安装只保存文件，不自动执行脚本。`ui` 文件当前只作为资源保存，**不会自动挂载成 UI**；
  已有交互入口仍按 `ui.contributions` 的宿主协议和权限运行。
- 编辑既有插件保留资源与 UI 声明。当前工作流编辑器不能表达的节点会明确拒绝编辑，
  不会静默转成 AI 节点。

普通 /插件 调用仍保持单 Agent 方法执行，不会悄悄切换成工作流。

### 本机逐节点调试

安装个人工作流后，在当前对话输入 /调试插件，或选择插件后点击“逐节点调试”。
调试卡在对话内呈现，不新建任务，不新建第二条会话，不打开独立调试窗口。

- 开始前明确确认插件、版本、公开参数和调试说明。可带入当前会话文字、历史附件、待发送的截图和文件。
- 按依赖顺序逐节点调用本机 Runner；节点可选择不同的已支持本机 Agent 和模型。
- 沿用企业模型授权、设备能力授权与 Skill 策略；每个节点只申请声明的 MCP 子集。
- AI 的正文和工具过程进入现有消息流。文件与决定类产出逐项校验，交接时再次核对 SHA-256。
- 审批卡可直接查看已校验文件；Markdown、文本、JSON、CSV 等在卡内预览，其他文件沿用系统打开。历史相对路径附件按原会话目录解析，并检查真实路径边界。
- human_review 必须由当前对话所有者明确确认；未确认、失败、断线状态不明时，后续步骤和普通消息队列都不越过。
- 重试只针对失败节点，遵守节点重试上限；停止必须先确认执行机状态。
- 本机日志记录固定插件版本、节点尝试与运行标识。刷新可重新打开调试卡；主进程重启后必须显式恢复，已完成节点不重复派发。
- 工作文件位于当前会话的 plugin-debug/<runId>/<node>-<attempt>。本机 publish 节点仅表示调试办结，不进行企业上传、审批或上架。

边界：此入口是个人工作流的本机调试，不改变正式企业工作流的服务端编排；
不支持把 hosted 路由或远程执行机标签降级成本机运行；Git 提交锁定的代码审查仍需企业代码工作流验收，本机入口会明确阻断而不会假装通过。自定义 HTML UI 资源仍不自动挂载，
插件编辑器之外的脚本/部署节点也不会被静默执行。真实多底座和企业审核发布仍需分别验收，
不能仅凭本机调试通过就宣称完成企业发布。

把 `plugin.json`、可选的 `workflow.json`、Skill 和资产放在包根目录后压缩：

```text
my-team-flow.soduwork-plugin
├─ plugin.json
├─ workflow.json          # 可选
├─ skills/                # 可选
└─ README.md              # 可选
```

然后在管理端“插件中心 → 导入插件”选择包。建议先下载管理端提供的起步包修改，
因为它会随当前 schema 和安全策略同步更新。
注意：本机调试记录可跨主进程恢复，不代表既有普通待发送消息队列也已持久化。后者目前仍在进程内，关闭客户端前应先完成或保存待发内容。

## H5 应用对话与刷新

应用可引入公共 `client/sdk/soduwork-app.js`，通过 `soduWorkApp.chat.send({text,requestId})` 向自己的原生侧栏发送业务任务。跨域直接 iframe 用 postMessage，顶层显式授权精确来源，子页指定 parentOrigin；使用说明、发送回执与刷新事件见 [H5 SDK](../client/sdk/README.zh-CN.md)。无需增加面向用户的技能选择器，页面业务动作携带上下文，插件按自然语言匹配技能。`conversation.send` 与 `composer.control` 必须由插件的 source.bridge.capabilities 明确声明。

### 应用专属设置与 ukey

本机应用在 `source.bridge.capabilities` 声明 `settings.read` / `settings.write` 后，可通过公共 SDK `soduWorkApp.settings.get/update` 同步任意 JSON 业务参数。与应用设置面板共用按账号/应用/来源隔离的加密存储；显式读取自己应用的 ukey 可恢复业务登录，退出页面保留壳内凭据。原生顶层自有 MCP 使用 `credentialKey:'ukey'` 引用设置，技能继续走每轮受控 MCP，不接触密钥。跨域 iframe、凭据读写、CAS 与换号旧授权失效的完整合同见 [H5 SDK](../client/sdk/README.zh-CN.md)。凭据不属于草稿 setup，不随版本/导出包或提示词分发；没有两套用户的 SSO 同步。

## 文件身份与签名升级

插件和导入 Skill 使用 `sha256-file-tree-v2`，API 仍返回 64 位十六进制摘要。SHA-256 的输入依次为 ASCII 域标识 `soduwork.file-tree/v2`、一个 NUL 字节、64 位大端无符号文件数，再按路径的 Unicode 码点顺序逐文件写入：64 位大端 UTF-8 路径字节数、路径字节、64 位大端内容字节数、内容字节。路径使用 `/`；目录条目、ZIP 顺序、时间戳和压缩方式不影响身份。签名内容只排除 `soduwork/signature.json`，完整包身份仍包含它。明确的长度边界防止二进制内容冒充其他文件条目。

新发布者证明使用 `soduwork.plugin-signature/v2` 和 Ed25519。Hub 签名准备接口、桌面签名器和包解析器应一同升级。即使旧签名在数学上有效，v1 证明也会被拒绝；仅修改 schema 标签不能完成升级。

升级保留原始插件包、Skill 目录以及历史索引和数据库记录。旧版插件身份不能加载包资源或内置 Skill，历史已验证发布者证明显示为 `legacy-signature`。请向发布者获取原始来源，核对完整文件树，提升插件语义版本号，去除旧签名，对新准备的 v2 载荷重新签名，再导入并审核新版本。未签名插件也须提升版本号重新导入；旧不可变版本不会被重写。

旧版导入 Skill 仍在列表中显示，并提供需要重新导入的身份错误；执行、共享和传输会被阻止。核对完整原始 Skill 包后重新导入，只更新生效指针并保留旧目录；共享 Skill 需重新提交审核。Hub 和 Runner 技能缓存使用独立 `v2` 命名空间，旧就绪标记和恢复的会话不能提供旧缓存内容。升级时不要删除保留的原文件，应留作检查和备份。
